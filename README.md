# awesome-site-data

Collection data for [awesome-site](https://github.com/HagiCode-org/awesome-site): the collection registry, topic catalogs, GitHub-only candidates, source review ledger, reviewed translations, pinned upstream README sources, and the translation tooling that produces them. The framework consumes this repository as its `data/` submodule, so the layout below is a contract: `awesome-site` reads these paths directly.

## Layout contract

| Path | Contents |
| --- | --- |
| `content/awesome/collections.json` | Collection registry: each imported source, its `sourceDir`, catalog, and tags |
| `content/awesome/catalogs.json` | Stable topic keys with nonempty labels for `root` and the nine locales |
| `content/awesome/candidates.json` | GitHub-only candidates that have no hosted collection edition |
| `content/awesome/source-reviews.yml` | Source review ledger (imported sources, candidates, README rights notices) |
| `content/awesome/readme-rights-reviews.yml` | Pinned README and license rights review records for candidates; no pipeline code reads it, and `source-reviews.yml` is the validated ledger |
| `content/awesome/<id>/translations.json` | Per-collection locale metadata and the `sourceDigest` of the mirror README |
| `content/awesome/<id>/mirror/README.md` | Tracked mirror of the pinned upstream README with ledgered cleanup edits applied; the English source the site publishes |
| `content/awesome/<id>/mirror.json` | Mirror ledger: upstream revision and digest, mirror digest, and cleanup edits |
| `content/awesome/<id>/locales/<locale>.md` | Reviewed translated README bodies |
| `sources/<id>` | One pinned upstream source per imported collection (nested submodules), read for provenance and license; never edited |
| `.gitmodules` | Registrations for the `sources/<id>` submodules |
| `scripts/mirror.mjs`, `scripts/mirror.test.mjs` | Mirror sync, check, and diff tooling and its tests (Node built-ins only) |
| `scripts/mcp-translate.mjs`, `scripts/_mcp/` | Translation tooling for the MCP servers collection |

Every collection `<id>` in `collections.json` has a matching `sources/<id>` registration in this repository's `.gitmodules`, and its `sourceDir` points at that path. Git records each source's exact commit as a gitlink, so an upstream commit does not change a build until the gitlink is deliberately updated here.

## Clone and initialize

```sh
git clone --recurse-submodules https://github.com/HagiCode-org/awesome-site-data.git
# For an existing checkout:
git submodule update --init --recursive
```

Sources are cloned from their upstream repositories at the pinned commits. Do not run `git submodule add` for an existing source; that re-clones and moves the pin.

## Content ownership and locales

The homepage and collection pages in every locale are generated by `awesome-site` from this registry, reviewed translations, topic catalogs, and candidates. The framework owns the generated pages; this repository owns only the inputs. Each collection needs a reviewed translation for each of the nine non-English locales before it is published, and the English source is the collection's mirror README: the pinned upstream README with any ledgered cleanup edits applied.

`content/awesome/collections.json` is the collection registry. Each imported source is a pinned submodule under `sources/`; the original source is `awesome-github-profile-readme`. The source review ledger records the imported sources, GitHub-only candidates, and the three documented exclusions: `awesome-redis` (746 stars at the 2026-10-03 review), `awesome-kotlin` (its README is an introduction, not the collection), and `awesome-public-datasets` (its README is reStructuredText). Git records each selected source's exact commit, so later upstream commits do not change a build until the gitlink is deliberately updated.

`content/awesome/candidates.json` lists qualifying repositories that do not yet have a hosted collection edition. The candidates have a reviewed repository license matching the pipeline's supported allowlist; their `licenseId` and dated star count are recorded in the registry and validated by the pipeline. Candidate entries in `content/awesome/source-reviews.yml` also record the reviewed README/license commit and blobs, README rights notices, embedded-asset counts, and remote asset hosts. These checks do not independently clear third-party material or prove a repository license covers every README asset. All candidates remain GitHub links only: the site does not copy or translate their README or embedded assets.

Each collection registration requires `catalog` as one topic key or an array. `content/awesome/catalogs.json` defines stable topic keys and nonempty labels for `root` and all nine locales. Docs may also provide `tags`; effective tags preserve explicit tag order and append catalog keys, with duplicates removed. Every effective collection tag must exist in the taxonomy. Technology names may keep their usual spelling across locales; translate human topic labels.

Reviewed translation inputs live under `content/awesome/<id>/`. Generated pages are owned by `awesome-site`; do not add or edit them here.

## Source review ledger

[`content/awesome/source-reviews.yml`](content/awesome/source-reviews.yml) is the canonical maintainer record of source review outcomes. Each YAML sequence entry includes `id` (stable kebab-case identifier), `source` (canonical GitHub repository URL), `title`, `imported` (a boolean), `notImportedReason`, and `importedAt`. Candidate entries also include the README rights review fields. Repository identities are compared case-insensitively.

`imported: true` means the matching source is admitted to `collections.json`. A checked-out submodule or a GitHub-only candidate is not an import. Imported records have `notImportedReason: null`; non-imported records require a reason and `importedAt: null`. For example:

```yaml
- id: pending-source
  source: https://github.com/example/pending-source
  title: Pending Source
  imported: false
  notImportedReason: "Pending confirmation of redistribution permission."
  importedAt: null
- id: excluded-source
  source: https://github.com/example/excluded-source
  title: Excluded Source
  imported: false
  notImportedReason: "Excluded by the documented eligibility threshold."
  importedAt: null
```

When an imported source's admission time is known, record it as a quoted UTC timestamp such as `"2026-10-03T19:00:00Z"`. Use explicit `importedAt: null` for unknown historical timing; null does not mean the source is unimported. The migrated records use null where repository history did not establish a reliable admission time. Do not substitute an audit date, submodule checkout time, or build time.

When admitting a source, update its hosted registration and review record together, then record the known admission time. Re-review does not refresh that time. When removing a source from the hosted registry, set `imported: false`, explain the removal, clear the current import time, and update any candidate registration as appropriate. The pipeline checks both registries against the ledger and never changes any of them automatically. Review status does not grant redistribution permission or bypass license, safety, or translation checks.

Onboard a listed repository from this repository's root with `git submodule add https://github.com/<owner>/<repo>.git sources/<id>`, which checks out the remote's current default-branch HEAD and records that exact commit. Record its GitHub star count and canonical one-file README in the dated audit snapshot. Missing LICENSE files do not automatically disqualify a star-qualified candidate, but a license or explicit permission confirming redistribution is still required before copying the README into published content. The current verifier recognizes `CC0-1.0`, `MIT`, `Apache-2.0`, `Unlicense`, and `WTFPL`; do not infer permission from a missing or ambiguous license. Also verify source language and safety compatibility. Unverified permissions, rejected content, or missing reviewed translations keep that collection out of the published set.

## Mirror and cleanup edits

Each registered collection has `content/awesome/<id>/mirror/README.md`, a tracked copy of its pinned upstream README. The site publishes the mirror, so the pinned `sources/<id>` checkout stays unmodified. With no ledgered edits the mirror is byte-identical to upstream.

`content/awesome/<id>/mirror.json` binds the mirror to its source and lists every cleanup edit:

```json
{
  "version": 1,
  "upstream": { "revision": "<pinned commit>", "readmePath": "README.md", "digest": "<SHA-256 of upstream bytes>" },
  "mirror": { "path": "mirror/README.md", "digest": "<SHA-256 of mirror bytes>" },
  "edits": [
    {
      "id": "remove-example-entry",
      "category": "political-sensitive",
      "reason": "Why the passage is removed.",
      "reviewer": "Reviewer name",
      "reviewedAt": "2026-10-11",
      "find": "exact upstream text that occurs exactly once",
      "replace": ""
    }
  ]
}
```

Each `find` must occur exactly once in the upstream README, edits must not overlap, and an empty `replace` removes the text. Edits are the only way the mirror changes; never edit `mirror/README.md` by hand. Run these from this repository's root:

```sh
node scripts/mirror.mjs sync                     # all registered collections
node scripts/mirror.mjs sync --collection <id>   # one collection
node scripts/mirror.mjs check                    # regenerate in memory and compare byte for byte
node scripts/mirror.mjs diff --collection <id>   # unified diff of upstream against mirror
```

`sync` requires each source to be initialized, clean, and at its pinned commit. It writes through a staging directory, so a failed run leaves existing files unchanged. `check` fails with the collection id on a stale or hand-edited mirror and prints the collections with edits and their counts.

## Translate or update a collection

Export a translation work package from the `awesome-site` checkout, which reads this repository's registry and sources, without overwriting existing files:

```sh
npm run content:export -- --collection awesome-github-profile-readme --output /tmp/agpr-translation
```

The export contains the mirror README (the English source the site publishes), the upstream license, the pinned revision and upstream digest, whether the mirror carries cleanup edits, the mirror's SHA-256 source digest, the target locale list, and full-coverage instructions. Translate the complete mirror for each target locale, never the raw submodule file. Preserve names, code, list/table entries, link and image destinations, and section order. Store each body at `content/awesome/<id>/locales/<locale>.md`.

For every locale, record a localized `title` and `description`, the current `sourceDigest`, `reviewStatus: "reviewed"`, and a truthful `isAITranslation` boolean in `content/awesome/<id>/translations.json`. AI translations must set `isAITranslation: true`; the published edition then shows an AI-translation disclosure. Builds validate review status and structure but do not contact translation services or claim that structural checks prove linguistic quality.

Run the content gate in `awesome-site` against this data before building:

```sh
npm run content:check
npm run content:prepare
```

If the upstream revision or a ledgered edit changes the mirror, export it again and update all translations to the new mirror digest. When an edit removes a passage, delete the same passage from every locale body, because a translation that still carries it fails the content gate. Missing, stale, unreviewed, unsafe, or structurally incomplete content fails with a collection/locale diagnostic before generated pages are replaced. Fix the reported inputs and rerun preparation; authored files and the previous generated set remain intact on validation or staging failure.

## Changing data and bumping the pin

1. Move each changed `sources/<id>` gitlink, then refresh its mirror with `node scripts/mirror.mjs sync --collection <id>` and review `node scripts/mirror.mjs diff --collection <id>`. If a ledgered `find` no longer matches the new upstream text, sync fails; update that ledger entry, never the mirror. Refresh every changed mirror before committing.
2. Run `node scripts/mirror.mjs check` and `node --test scripts/mirror.test.mjs`, then commit and push the change here to `main`. Commit collection, mirror, ledger, translation, and source-pin changes together when they belong to one admission, removal, or pin bump.
3. In `awesome-site`, move the `data/` submodule to the new commit: `git -C data fetch origin main && git -C data checkout <commit>`, then `git submodule update --init --recursive`. A mirror that was not refreshed fails `npm run content:check` with a stale-mirror diagnostic.
4. Run `npm run content:check`, `npm run check`, `npm run build`, and `npm test` in `awesome-site`, then commit the `data` pin there.

`awesome-site` pins one commit of this repository. A later data commit does not reach a published site until that pin is committed in `awesome-site` and its publication workflow passes.

## Political-sensitivity audit

First pass over the 76 registered collections, recorded 2026-10-11 for the `political-sensitive-data-cleanup-mirrored-submodule` change. At baseline each mirror was byte-identical to its pinned upstream README, so the audit read the pinned upstream text.

Scans, run case-insensitively over every `content/awesome/<id>/mirror/README.md`:

- Broad scan of country, conflict, party, government, and military terms, including `ukrain`, `russia`, `palestin`, `gaza`, `israel`, `hamas`, `politic`, `government`, and `military`: 248 lines across 59 files.
- Armed-conflict and partisan terms: slogans such as `glory to`, `slava`, and `stand with`; `free palestine`, `free tibet`, `genocid`, `occupation`, `invasion`, `nazi`, `fascis`, named leaders, parties, and armed groups; `propaganda`, `boycott`, `sanction`, `regime`, and `democrat`, `republican`, `socialis`, `communis`, `capitalis`: 103 lines.
- Non-Latin terms in Chinese (`政治`, `政府`, `战争`, `俄罗斯`, `乌克兰`, `以色列`, `巴勒斯坦`, `台湾`, `习近平`, `共产党`, `独裁`, `侵略`, `英雄`, and related terms) and Cyrillic (`войн`, `Путін`, `Україн`, `Героям`, `нацист`, `фашист`, and related terms): 23 lines.
- Campaign and call-to-action terms: `fundrais`, `gofundme`, `patreon`, `crowdfund`, `liberat`, `resistance`, `justice for`, `freedom for`, `troops`, `motherland`, `war crime`, `massacre`, `apartheid`, `regime`: 14 lines.

Every hit was read on its line in context, and the three lines the tool truncated were read in full.

No hit endorses one side of an armed conflict, calls for violence, runs a support or donation campaign for a party to a conflict, or makes a partisan political statement. Each is a neutral use:

- Computing, security, and tooling vocabulary, such as "distributed computing", "modify", "Swiss Army knife", "Capture the Flag", "Simian Army", and "Docker Pirates ARMed with explosive stuff" (a blog name).
- Language, country, and location labels, such as "NLP in Ukrainian", Russian- and Ukrainian-speaking community channels, "National Taiwan University NLP Lab", and the privacy-list service locations "Based in Ukraine" and "Based in Russia".
- Research resources and references, such as the "Columbian Political Speeches" dataset, military doctrine publications and CISA and ISAO information-sharing references in threat intelligence, and "AI Fraud Investigation Agent".
- Project funding unrelated to any conflict, such as the Django Software Foundation donation link.
- Persuasion and security material, such as the dark-psychology skills entry that cites CIA and FBI source books, and the "Geopolitic Explainer" GPT listing.
- Tool directory entries, such as Riseup, described as serving groups working on social change; the entry makes no political claim.
- Prompt collections: a comedy prompt that asks for jokes about politics without taking a side, an IELTS essay prompt, and a video title that contains 英雄主义 (heroism).

Decision: no ledger edits. Every `mirror.json` keeps `"edits": []`, no locale body or `translations.json` changed, and every mirror stays byte-identical to its pinned upstream.

Limits: keyword scans can miss sensitive text that uses other words or other languages. This record covers the pinned revisions as of the date above. A pin bump or new upstream text needs a new scan, and this section is updated with the new date.
